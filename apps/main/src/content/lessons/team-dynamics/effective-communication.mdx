# High-Bandwidth Communication

Communication in engineering transfers mental models. When one engineer describes a design, the goal is not only that the listener hears the words but that the listener builds a model of the system that matches the speaker's. Most communication failures are mismatches between those models. Each party believes the other agrees, and the disagreement appears later, usually in code or in production.

Herbert Clark and Susan Brennan (1991) describe communication as a process of *grounding*: speakers and listeners jointly establish that a message has been understood. Grounding takes effort, and the channel determines how much effort it costs. Face-to-face conversation provides immediate feedback through facial expression, pauses, and interruptions. A written comment provides almost none, so the author has to anticipate misreadings.

## Choosing a Channel

Synchronous and asynchronous communication suit different purposes.

- **Synchronous** channels include meetings, pair programming, and instant messaging. They provide fast feedback and are appropriate when a topic is ambiguous, urgent, or emotionally sensitive. A disagreement about a team's priorities usually needs a live conversation, because the nuance is hard to convey in text.
- **Asynchronous** channels include email, pull request comments, and design documents. They allow careful thought, create a record, and do not interrupt anyone. They suit deep technical work, documentation, and updates that do not require an immediate response.

A common error is to use a synchronous channel for an asynchronous purpose. A design question sent as a chat message and answered in three quick exchanges leaves no record and often produces an answer that the wider team never sees.

## Giving Feedback in Code Review

Code review is a social interaction before it is a technical one. Sadowski and colleagues (2018), describing code review practice at Google, note that the process serves knowledge sharing and team cohesion as well as defect detection. A reviewer who sounds dismissive can discourage a colleague even when every comment is correct.

Several practices reduce this risk.

- **Describe the code, not the person.** "This function mixes parsing and validation" is more useful than "You made this hard to follow."
- **Explain the reason.** A comment that says "use a map here, because lookups happen in a hot loop" gives the author something to evaluate. A bare instruction gives them only something to obey.
- **Separate blocking issues from suggestions.** Mark which comments must be addressed before merging and which are optional. Authors who cannot tell the difference tend to either over-correct or ignore everything.
- **Ask before asserting.** "Is there a reason this handles only the first element?" invites an explanation. It may reveal a context the reviewer lacked.

## Active Listening

Listening is the other half of communication, and it is harder to observe. Three techniques make it deliberate.

- **Mirroring.** Restate what you heard in your own words. "So the concern is that the cache can return stale data during deployment?" lets the speaker correct a misunderstanding before it becomes a design decision.
- **Open questions.** Ask questions that require an explanation rather than a yes or no. "How does this path behave when the upstream service times out?" reveals more than "Does this handle timeouts?"
- **Acknowledging the other view.** You can recognize a person's point without agreeing with it. "That tradeoff matters for the on-call team, and I think it is outweighed by the latency cost" shows that the point was heard and weighed.

## Example: A Design Disagreement Resolved in Writing

Two engineers disagree about whether a service should use a relational database or a document store. In a chat thread, each restates a position, and the disagreement grows. The team lead asks both to write a one-page comparison that lists the query patterns, the consistency requirements, and the operational costs of each option. Once the document exists, the disagreement narrows to two specific questions about query patterns, which the team can test.

The written artifact did not remove the disagreement. It made the models explicit enough to compare. That is the purpose of high-bandwidth communication: not more messages, but messages that let two people's models converge.

## Exercise

Choose a recent technical disagreement you were part of or observed. Identify where the models diverged: what each person assumed about requirements, constraints, or the system. Write a three-sentence summary that a neutral reader could accept as both parties' positions. If you cannot write it, that is evidence that grounding did not happen.
